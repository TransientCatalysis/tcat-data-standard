# Contributing

Read [`STANDARD.md`](STANDARD.md) first — it is the rulebook, and each rule says why it exists rather than only what it requires.

Three institutions pin this repository for the definition of ingestible data. That is the whole reason it is small, boring, and slow to change. A change here can invalidate data at PSU, BNL, and GT simultaneously, so the bar is higher than it looks for a repository this size.

## Setup

```bash
pip install -e ".[dev]"
pytest                                    # 257 tests
tcat-validate all examples/
```

## The most common contribution: a field the schema does not have

**You are not blocked.** Put it in `extensions` — the validator ignores that object rather than rejecting it — and [open a schema-change issue](.github/ISSUE_TEMPLATE/schema-change.md).

```json
"extensions": { "psu": { "mfc_calibration_date": "2026-08-30" } }
```

Promotion threshold: the **same field, independently, in three labs' extensions**. Schema follows practice; it does not predict it. Two labs is a conversation, not yet a schema change — and a field promoted from one lab's usage is a field the other two will fill in wrong.

If the validator rejects something it *should* accept, that is a bug here, not in your data. Say so in the issue.

## Changing the schema

```
patch  clarification, no structural change
minor  adds OPTIONAL fields only; all existing data stays valid
major  breaks existing data. Rare. Ships a migration script rather than a demand.
```

**Required-vs-optional is the decision that matters**, and there is one test for it: *would retrofitting this later lose information that cannot be recovered?*

`status` and `batch_id` are required because a deleted failed run and a lost batch grouping are gone forever. Almost nothing else is like that. If a field can be backfilled from other records, from a lab notebook, or by asking someone — make it optional and let the validator warn.

### A bump is not always needed

Increment when somebody else could be holding the old bytes — cloned, forked, or
branched between pushes. If not, amend in place; an unnecessary version number is
ceremony, and it makes the real ones harder to read.

For the schema specifically the question is sharper: **does any document declare
that version?** If one does, it is a consumer regardless of who cloned what, and
amending is exactly the silent reinterpretation `schema_version` exists to
prevent. See STANDARD.md §6.

### Version retention

Versions live in `src/tcat_standard/schema/<version>/` and **are never removed or edited**. A dataset declaring `0.1.0` is validated against `0.1.0` for as long as this repository exists, so a bump never obliges a lab to rewrite data.

Retention applies from the **first tagged release**. `0.1.0` is a pre-release draft under team review and may still be amended in place — after the first tag, that stops.

### Adding a document kind

1. `src/tcat_standard/schema/<version>/<kind>.schema.json`, with `$schema` and a versioned `$id`
2. Register it in `KINDS` in `schema.py`
3. `validate_<kind>` in `validate.py`, exported from `__init__.py`
4. Kind inference in `cli.py` — both the directory map and the contents fallback
5. An example in `examples/`, generated by `make_examples.py`
6. Tests

Step 5 is not optional. An example is how a collaborator learns the shape, and a generated one cannot drift away from the schema.

## Every field needs a description that says *why*

Enforced by `test_every_documented_field_has_a_description`, and it catches real omissions every time someone adds fields.

Not this:

```json
"batch_id": { "type": "string", "description": "The batch identifier." }
```

This:

```json
"batch_id": {
  "type": "string",
  "description": "REQUIRED (TRACE-AI B2). Groups data that must never be split across a train/test boundary -- one synthesis batch, one catalyst charge, one beamtime. A validator cannot enforce grouped splits unless this exists, and it cannot be reconstructed after the fact."
}
```

A schema is documentation for three institutions. An undescribed field gets filled in by guessing from its name; a field whose description says only what it holds gets filled in inconsistently. The description is where the *reason* lives, and the reason is what stops someone removing the constraint later.

## Errors vs warnings

This distinction is load-bearing and easy to get wrong.

**Errors fail CI.** Only for things that make data unusable or unrecoverable.

**Warnings never affect exit status.** For things that are valid and probably unwise: empty `notes`, a metric with no interval, an ungrouped split, a model with no stated limitations.

The moment style advice can block a merge, people stop running the validator locally and start discovering it at the worst possible time. A warning that "should really" be an error is a request to make the schema require it — which is a versioning decision, not a validator tweak.

The exception, in `_structural_errors`: a rule JSON Schema enforces correctly but describes unreadably gets a second, human-phrased error. Same rule, better message. Never a new rule.

## Tests

Style, following what is already here:

- **Test names are sentences.** `test_a_channel_cannot_have_a_unit_without_an_uncertainty`.
- **A docstring when the reason is not obvious from the name**, explaining what breaks if the property fails. That is what makes a test survivable when someone later wants to simplify the thing it protects.
- **Assert the negative.** A suite full of positive assertions still passes when the validator has silently stopped rejecting things. One fixture per missing required field, each failing with that field named.
- **Fixtures are generated**, by `tests/make_fixtures.py`, from the valid example — so an invalid fixture cannot drift and start failing for the wrong reason while still going red.

```bash
python examples/make_examples.py     # after touching the synthetic data
python tests/make_fixtures.py        # after adding a required field
```

CI checks the regenerated output is committed and unchanged.

## Moving the TRACE-AI pin

Not a dependency bump. Revised item wording changes what we are *claiming to satisfy*, so re-read [`profiles/trace-ai/crosswalk.md`](profiles/trace-ai/crosswalk.md) and [`enforcement.md`](profiles/trace-ai/enforcement.md) before touching `pin.json`, and record the reason in the changelog.

## Before opening a PR

```
[ ] pytest passes
[ ] Every new field has a description saying WHY it exists
[ ] Required vs optional decided by the retrofit test, and justified in the PR
[ ] STANDARD.md version header, changelog table, and LAST_REVIEWED updated
[ ] Old schema versions untouched
[ ] make_examples.py and make_fixtures.py re-run, output committed
[ ] CHANGELOG.md updated
[ ] The PR says which spokes have to do something -- "none" is the preferred answer
```

## Downstream

`tcat-analysis` pins this package; `tcat-index` validates every record against it; every spoke's CI installs it. **The dependency runs one way and has no exceptions.** If a feature elsewhere seems to require a change here, that is evidence the schema is wrong — not that the boundary should be crossed.
